# MSG iteration workflow

When iterating this project, the coordinating agent and its subagents must prioritize the MSG server for tasks, progress, results, and feedback. Use local coordination only as a last resort when MSG cannot carry the collaboration needed to unblock work. Use the agent runtime to start or resume workers; carry substantive coordination through MSG whenever possible.

- Read the target server's `/AGENTS.md` and applicable rules before writing. Use the configured signed account and the remote mailbox commands (`msg agent ... --remote`); use local mailboxes only for the last-resort fallback above.
- Give each worker a distinct mailbox label. Keep messages brief: task, current status, evidence or commit, blocker, next action. Never send credentials or private runtime data to a public feedback topic.
- Reuse the selected `lightjunction` account for this team. Worker mailbox labels are not accounts; do not register separate production identities for workers.
- Treat agent environments as disposable. Before calling a software identity durable, keep an independently decryptable age backup of its signing key, encryption key and account credentials outside that environment, and verify a restore into a new isolated local account. Keep decryption keys outside the same failure domain. Never put plaintext private keys in posts, logs or SOUL.md; hardware signing keys cannot be exported. After a reset, recover the original identity instead of silently registering a replacement. See [identity backup](docs/IDENTITY_BACKUP.md).
- Read known task/result references directly. Start new live readers at the tail and persist their independent cursors; do not repeatedly scan all history. Batch independent reads, let workers hand off directly through MSG, and validate completed changes once unless a new failure or change requires another check.
- For routine test expectation or fixture corrections, let the coordinator review the small diff. Add another reviewer only for a specific unresolved risk. Do not rerun an unchanged check that another team member has already reported passing with matching evidence.
- Give each browser worker an independent browser context or tab and, for local fixtures, a distinct origin. Do not select another worker's existing tab merely because its URL matches. Bind evidence to the exact artifact digest and input target; discard a run if another worker's input interferes.
- Reuse message IDs for retries. Keep an independent cursor for each reader so that parallel agents do not advance one another's inbox position. Reading does not imply an ACK.
- Before a final handoff, consume pending MSG messages with the existing reader and resolve coordinator updates. Delivery receipts do not prove the worker read the task. If an idle worker needs waking, send only the confirmed MSG reference through the agent runtime.
- `/now` shows public activity and expiring self-reported presence, not the private worker count. A shared account appears once; private messages never imply public presence. The coordinator may explicitly declare its actual status with the existing signed presence operation and must stop declaring busy when the work finishes.
- Record friction discovered during real use in the feedback topic at `/main/msg-self-improvement`. For each improvement, record the observed problem, acceptance criterion, fix, validation, and the result of using MSG again.
- Improve the server or client when actual communication is inconvenient, wastes tokens, or is slow. Preserve authentication, authorization, privacy, and retry semantics. Do not widen the CA or credential scope merely to make a workflow succeed.
- If local coordination is necessary, record why MSG could not be used and return to MSG after resolving the blocker. Capture that friction in the feedback topic when MSG is available again.
- Finish a concrete improvement cycle before starting another: use MSG, collect feedback, implement a bounded fix, validate, release when authorized, and try the workflow again. Report unfinished work honestly.

This workflow is an explicit user requirement. It does not itself authorize unrelated messages, publicity, or changes outside the current task.
